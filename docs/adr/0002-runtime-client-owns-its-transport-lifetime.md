# The runtime client owns its transport's lifetime

A generated module creates its client at import and keeps it until the process ends, and nobody can close it: the module has no owner. So the lifetime of connections is owned by the runtime client itself, and the module and its consumers do not know about it. `GQLClient` holds a pool and closes it itself when the garbage collector collects the client or the interpreter exits (`weakref.finalize`). `AsyncGQLClient` holds a separate transport per event loop, because an `httpx2.AsyncClient` pool is bound to the loop in which it opened the connection. A loop's transport is closed by an async-generator hook, which `shutdown_asyncgens` runs when the loop shuts down normally (`asyncio.run`, `asyncio.Runner`, dlt). An explicit `close()` is terminal: after it the client works in no loop. `close()` does not touch other loops' transports — their hooks will close them. The generator, `use_client` and the module's public names are unchanged by this decision.

As the price of this decision we accept four limitations. A loop shut down manually without `shutdown_asyncgens` leaves its transport to the garbage collector, which emits a `ResourceWarning` even though requests work. Entries of stopped but not closed loops can accumulate. After `fork` the child process inherits the open pool, as it did before this decision. `shutdown_asyncgens` closes a loop's async generators all at once and in arbitrary order, so an operation that another generator's cleanup starts at that moment may find the loop's transport closing. If the transport is already closed, the operation opens a new one that the loop shutdown never reaches, and that one also goes to the garbage collector. Waiting for in-flight operations was rejected: it does not catch operations started after closing.

## Considered Options

- **A public `close()` on the module** — closing relies on every consumer remembering it, and the async client still breaks when the loop changes. Rejected.
- **A client per operation, a pool only on an explicit client, and a swap stack in `use_client`** — the class of problems becomes unrepresentable, but the solution is complex, and every request pays for a new connection (+0.7…3 ms in probes on loopback without TLS). Rejected for complexity and performance overhead. The swap stack served the per-operation client here; it was later adopted separately against overlapping swaps — ADR 0005.
- **Drop the old transport without a hook when the loop changes** — every connection of a dead loop produces a `ResourceWarning` on garbage collection, including after an ordinary `asyncio.run`. Under consumers' `filterwarnings = error` this can fail a random test. Rejected.
- **A lazy singleton or a caller-owned client** — laziness by itself solves neither closing nor loop binding. A caller-owned client breaks every call site, and in dlt the caller does not own the loop. Rejected.

Reason to revisit — a consumer whose runner does not call `shutdown_asyncgens` uses the module's client against a real socket under `filterwarnings = error`. Another reason — trio is needed: it has no `asyncio.get_running_loop()`. On uvloop 0.22.1 the hook fires in both `asyncio.Runner` and `asyncio.run`; a probe confirmed this.
